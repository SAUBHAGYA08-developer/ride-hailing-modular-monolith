Ride Hailing Backend — architecture

A modular monolith. Eight database schemas, one deployable, and one rule that explains most of the design: Redis proposes, MySQL decides.

9 domain modules 8 MySQL schemas 16 Flyway migrations 134 Java classes 0 tests — the known gap

Every request crosses four gates before domain code runs

None of these live in a controller. Adding an endpoint inherits all four for free, which is why the controllers stay thin enough to read in one sitting.

Modules talk through published records, never entities

Each module owns one MySQL schema and exposes a small api package of records. Nothing outside a module sees its JPA entities, so a module's tables can change without a compile error anywhere else.

The booking pipeline — where the concurrency guarantee actually lives

Eight steps. Only one of them makes the system correct under concurrent load, and it is not the lock.

Redis — volatile, expiring MySQL — durable, authoritative rejection path

Pricing is a pipeline of pure steps, then a snapshot

The pickup — never the drop — selects the zone, so a fare cannot shift under a rider mid-ride. The numbers are from a real booking: 28.005 km, sedan, a 10 % coupon capped at 100.

What lives where, and what survives Redis dying

The split is not arbitrary: anything whose loss or duplication would be a real-world error lives in MySQL. Redis holds what the next few seconds of traffic can rebuild.

ConcernStoreKey or tableIf Redis is unreachable
Driver position Redis driver:locations GEO + a 60 s freshness key Pings 503 and are dropped; nobody is discoverable, so bookings fail
Availability and reservation MySQL drivers.status + version Untouched — double booking is impossible either way
Booking coordination Redis lock:booking:user:{id} Booking fails on this hop; the idempotency key is released so a retry works
Idempotency MySQL idempotency_keys Untouched — replay must survive a restart
Rate limiting Redis ratelimit:{policy}:{subject} Fails open — traffic allowed but unprotected
Business configuration MySQL read through Redis configurations · config:{key} Falls back to MySQL directly — correct, just chattier
Fares, rides, coupons, audit MySQL six further schemas Untouched
Position recovery copy MySQL drivers.last_known_* Reseeds the GEO set at startup — written on going online and when a ride ends, never per ping

Why a GPS ping must never reach MySQL. The drivers row is also the reservation row. Writing it several times a minute per driver would create a write hot spot and churn the version column that booking's conditional UPDATE compares against — turning every ping into a potential cause of a lost race.

Losing pings is acceptable because a position is a re-sent sample, not a fact. Losing a booking is not.

Where a change lands

The real test of this architecture is whether a new requirement lands in one place or five.

ChangeWhere it goesFilesDeploy?
New pricing tier or rateA row in pricing_distance_tiers, through the API0No
City-specific pricingA zone row pointing at a rule0No
Premium airport pricing inside a cityA nested zone at higher priority0No
Flat-discount couponA coupon row — FLAT already exists0No
Search radius, surge on/off, rate limits, cancellation feeA configuration row0No
Match by rating instead of distanceOne new DriverMatchingStrategy bean, chosen by config1Yes
New car type, e.g. SUVEnum + a migration for four CHECK constraints + substitution policy + a multiplier per rule5Yes

That last row is the honest weak spot. Car type is a compile-time enum guarded by database CHECK constraints — excellent integrity, but it makes the vehicle catalogue the one thing that cannot be extended without a deploy. If the catalogue is going to grow, it belongs in a table with foreign keys instead.
